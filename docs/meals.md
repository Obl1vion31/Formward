# 饮食记录

## 今天、历史与汇总

`/dashboard/meals` 默认显示设备时区的今天、四项摄入及今天餐次，跨日刷新。记录一餐默认今天；历史通过柱图或抽屉选择日期、补录、编辑、删除／恢复。顶部摘要始终是今天；合法 `?date=YYYY-MM-DD` 直接打开对应历史，非法日期忽略。总览另提供身体／摄入三图联动。

每天一根冷蓝 #7F9EAF 热量柱，纵轴从零起、单位 kcal，日期之间留白。图表上方常驻当前日期、热量及蛋白质／碳水／脂肪 g，默认范围内最近有记录的一天；悬停／聚焦更新读数，左右方向键选择相邻日期，点击或回车打开当天餐次。短区间在柱顶显示可容纳的数值，“连线”默认关闭，只连接相邻完整记录，缺日或不完整合计断开。保留 7D／30D／90D／全部／自定义，触屏默认 7D、桌面默认 30D；全部范围固定适配容器宽度，不横向滚动、不合并日期。上方显示完整起止日期，七天以内显示全部日期刻度，更长范围只显示当前选中日期。无记录留空，缺项只显示已知合计。

手动只提供食材库／自由填写两种入口。新餐项统一 `kind:food`，有 foodId／foodDraft 为食材库，否则为自由填写；自由项四项营养是本次实际摄入，分量可选，不再次相乘，可添加多项。旧 misc／whole 继续接受并保留，界面归为自由填写，用户编辑后的新版本统一为 food，不批量重写历史。AI 原有细分协议保持：misc 只估未单列剩余、每餐最多一个，whole 为唯一整餐项。初始化仍一行一餐，保留 whole／initialization 及原备注，未知品牌和地点为空，不提前创建食材。饮食日期按用户指定，不套用身体凌晨规则。

餐次编辑桌面使用宽双栏 Inspector，左侧完整食材搜索／列表，右侧本餐多项与合计；手机分为全宽选择和填写两步，保留草稿与搜索。食材选中或更换后清空用量并聚焦，不默认 1g；按重量填克数，按勺／份支持 0.5、0.8 等小数。旧餐项编辑读取自身快照的单位与营养基准。

## 食材与油酱

食材库直接列有效食材，名称、简短规格和实际基准数量常驻；蛋白质、碳水、脂肪、热量按列对齐，表头单位同行。营养值按该食材真实基准展示，不能把每包营养伪装成每 100g。依据、备注、来源和照片从最右侧“详情”打开只读抽屉；删除记录放入次级“最近删除”，可恢复，底层软删除与历史快照保持。

基础食材为鸡胸肉、去皮鸡腿肉、牛里脊、全蛋、养殖大西洋三文鱼和熟白米饭。界面只保留去皮去骨、生重／熟重、每 100g 等必要规格，不常驻额外油酱的冗长说明；原始数据与预设身份保持，避免重复采用及改变历史。数据来自 [USDA SR Legacy 官方资料](https://fdc.nal.usda.gov/download-datasets/)，标识及来源在 `food-presets.ts`。预设通过采用／foodDraft 确认加入本账号。

同单位按基准换算，每 100g 不能凭图片变成一份。热量独立保存，未知为 null，历史营养和计量快照不随食材更新改变。手动依据只有“标签／成分表”（reference）和“直接预估”（estimated），补充说明可选；AI 的 label／composition_table 仍须转录或来源链接，unknown 与旧来源不自动改写。描述只保留客观名称、每份分量与单位、成分和热量；估算食材保留成分分量、来源与计算、汇总结果，不写录入背景或凭空添加排除项。

纯食材、实际吃下的烹饪油、蘸酱分别记录。先核对做法与用量，再接受明确估算或未知；锅中投入的油不等于全部吃下，成品或整餐已经含油酱时不叠加。`amountDecision` 区分 provided、estimate_accepted、unknown_accepted；明确未知食量保留关联和 null 营养，不默认一份。

## 图片上传与恢复

每餐／食材最多 8 张、单张 20 MiB，支持原始 JPEG／PNG／WebP，不自动压缩。所有原图保存在 Private Blob，通过账号鉴权回看，不进入 public、Git 或营养 JSON 请求体。

MCP `import_meal_images` 和 HTTP `POST /api/v1/meal-images` 接受 ChatGPT files 引用，立即下载临时地址后私有保存，返回稳定 ID。最多两个下载并发，临时网络／5xx 最多重试一次，批次有截止时间；返回 complete／partial／failed、images、expectedImageCount 以及逐图 failures（index、code、stage、retryable、requestId）。部分成功保留已保存附件，只重试失败项。成功附件仍须加入对应餐次预览；已有餐次查询 id/version 后保留原内容更新。预览包含原图时应说明等待网页确认，确认后查询最新审核／餐次再报告关联状态，不把确认前文案当成实时状态。临时地址过期明确返回 image_url_expired，不能反复重用失效地址；服务端只下载允许的 ChatGPT HTTPS 文件域名，不接收任意外部／内网地址。除 oaiusercontent.com、chatgptusercontent.com、openai.com 的文件域名外，兼容 ChatGPT 的 oaisdmntpr 地区存储账号，例如 oaisdmntprnznorth.blob.core.windows.net 和 oaisdmntprwestus.blob.core.windows.net；Azure 账号名限 24 位小写字母／数字，限定完整前缀及 blob.core.windows.net 后缀。重定向每一跳重复校验，拒绝其他命名族、额外子域和伪装后缀。

网页使用 prepare → 短期 OIDC 预签名 → 浏览器直传私有 Blob → complete 登记。大图不经过 Vercel Function 请求体；凭据限定账号、随机路径、SHA-256、真实类型、大小和 10 分钟有效期，完成后核对实际字节，重复原图复用 ID。SDK 预签名流程不依赖 webhook。旧 multipart 客户端只兼容 4 MiB，需刷新使用新版直传。

网页显示进度、已完成缩略图、错误和“重试未完成照片”。失败保留输入与上传预期；“稍后补传”只清除上传阻断，保留缺图标识。餐次／食材 `expectedImageCount` 大于实际附件数时正常确认禁用，用户可补传后更新预览，或明确点击“先保存文字记录”；这个决定和缺图数进入审计，AI 不能自行忽略缺图保存。

内容摘要、user_id、组合外键和 feature 校验保护重复及归属。编辑、软删除恢复、食材快照与审计保留原图；移除附件不销毁审计引用。

## AI 录入与审核

流程：上传原图 → 识别 → 查已有食材 → 集中核对必要信息 → 带图预览 → 网页确认。缺日期、餐次、身份或实际食用量先问，明确的信息不重复问。包装／一盘须确认实际吃下多少；标签核对品牌、每 100g／每份／整包、kJ／kcal，并保留转录及换算依据。用户明确接受的生重、油酱估算写入依据，不继续伪装成未解决问题。

照片 AI 餐次 `photoReview` 包括 dateConfirmed、mealTypeConfirmed、identityConfirmed、amountConfirmed、cookingConfirmed 和 questions；未解决信息返回 needsUserInput 并阻止保存，缺图本身不替代这些事实核对。网页可逐项修改后更新预览。名称、规格、依据和备注只描述实际组成、称重口径与有依据的不确定性，不凭空罗列未提及的食物排除项，不把照片推断写成用户确认。无糖、去骨、过敏原等有来源且相关的规格保留。

审核常驻日期、餐次、记录项数、食材库／自由填写数量、每项数量和四项营养。名称、份量和热量优先展示，估算份量使用“约”，不重复显示来源标签。每行最右侧“详情”区分引用已有食材、确认后新增入库及直接记录，避免把预览解析出的临时 ID 当成已有食材；展开后查看食物识别、份量、油酱与营养分别来自用户、标签、食材库、成分表、估算或未知，附可核实说明、来源与不确定性；旧记录只展示已有依据，不补造详细推理。

保存后审核显示“已保存”和结果，移除待确认与确认按钮。客户端按操作 ID、revision 和终态更新，旧 pending 响应不能覆盖完成状态；可加载最新审核状态，页面刷新仍从数据库读取。待确认入口只列实际未过期的 pending 操作，独立未处理提交不会因为另一条已保存而消失。15 分钟预览、凭据撤销、归属、版本、快照和幂等保护保持。

## 代码与维护

网页、HTTP、MCP 复用同一 feature。`model.ts` 管 schema 与换算，`records.ts` 管事务／预览／确认，`images.ts` 管下载与私有存储，`image-upload.ts` 管直传凭据和登记，`photos.tsx` 管上传／回看，`review-details.tsx` 管营养明细与依据，`meal-review.tsx` 管审核状态，`meals-view.tsx` 管今天／历史，`meal-editor.tsx` 管两种录入与单位联动，`nutrition-fields.tsx` 管营养及手动依据，`nutrition-chart.tsx` 管固定宽度图表与读数，`presets.tsx` 管食材表格／详情。

饮食和身体 Inspector 共用遮罩手势判断，拖选内容到外部不关闭。仪表盘根滚动容器预留 scrollbar-gutter；共用弹窗锁定 html／body，仅补偿实际释放的滚动条宽度，切页和弹窗不改变内容横向位置。食材表格和餐项按容器宽度转成紧凑行，数字与单位保持同行；历史抽屉直接展开食物，餐名旁显示热量、不重复四格汇总，备注和来源按需查看，不撑宽页面。

数据库通过 `0015_meal_review_images.sql` 保存 nullable review_explanation 和 20 MiB 原图约束；`0016_silly_adam_warlock.sql` 仅扩展 foods_source_valid 接受 reference，旧来源与所有既有值保持。共享 migration 不修改，旧记录不补造依据或原图预期。备份、发布与验收见 [部署说明](deployment.md)，当前状态见 [交接](../handoff.md)。

已授权的说明修正使用 `scripts/correct-meal-text.mts` 和 feature 内的 `text-maintenance.ts`，不开放公开维护 API。私有请求指定账号、食材／餐项 ID、版本及前后文字，先预览后绑定摘要写入；只改文字与版本，旧餐项软删除留存，原始请求、旧审计、营养、份量和照片保持。事务保存 AI 代执行者与前后快照，重复执行幂等，版本／原文／身份冲突或审计失败整批回滚。脚本用法见 [维护脚本](../scripts/README.md)。


`scripts/maintain-foods.mts` 和 `food-maintenance.ts` 用于已授权的指定食材名称／说明与当前基准修正。预览绑定账号、ID、版本、关联餐次快照和摘要，事务写入并审计；原餐项软删除留存，原始请求与旧审计不改。当前 ON 标签基准为每 1 勺（约 30.4g），历史餐项的克数、单位、基准、营养和快照版本保持；仅与旧版本说明完全匹配的当前快照同步精简文字。Pasta Express 保留实际组成、各组食材的估计克数及整体热量范围和采用基准。不得按关键词批量重写历史。


食材详情以“估算分析”或“数据来源”为主体，不重复列表已有的四项营养表。估算依据保留组成与分量（含范围）、参考来源与可核实计算、整份结果；有标签／成分表时写来源标识和采用条目。未保存的分项克数／热量不补造，不用笼统一句估算取代已有分析，不写用户日期、上传或纠错经过，也不附泛化的生熟使用提醒。

`food-description.ts` 集中当前说明规则及明确污染文案的检查。新食材／foodDraft 含个人餐次背景或“不可直接套用／必须调整”等泛化提醒时，在建立预览前返回 `food_description`，可修正后沿用原 operationId 重试；个人备注仍可留在餐次，既有食材引用和历史快照不因该检查被改写。MCP search_foods 与 HTTP GET /foods 共用 queryFoods，每次实时返回 foodLibraryRules，避免只依赖客户端缓存的工具描述。自定义 MCP 元数据更新后应刷新连接并开新对话；刷新不会修改已保存文字。
