# 饮食记录

## 今天、历史与汇总

/dashboard/meals默认显示今天及以前最近有有效饮食记录的一天，并写明日期；部分营养未知仍保留最新日。网址指定日期和主动选择优先。记录一餐默认今天，按日期可直接补录。最近记录只列最近10个日历日，含空日；“查看全部”打开按50个有记录日期分页的历史窗口，也可选择任意日期。空日期不入库。总览是摄入／消耗及严格相邻晨重变化的双层图。

每日一根三色 kcal 堆叠柱，由下到上为 P 蛋白质 #365E78、C 碳水 #6C96B3、F 脂肪 #AFCDDE。默认按 P:C:F 克数占比分段，可切换 4P:4C:9F 能量占比；百分比与三色分段同步切换，柱总高始终为已记录 kcal，不改写原值。切换日期和区间保留口径，重新进入默认克数。宏量缺项或全部为零时只画总热量并注明占比不完整。容得下才标 P／C／F，读数列出 kcal、克数和占比。日期之间留白，固定宽度无横向滚动，短区间柱顶显示数值，长区间只显示选中日期和完整范围，可选连线默认关闭。 支持 7D／30D／90D／全部／自定义，饮食页手机默认7D、桌面30D；悬停／聚焦和方向键选日，点击查看餐次。无记录留空，未知不补零。

手动提供食材库与自由填写。新自由项默认1份，单位可选且放在份数前；例如鸡蛋每个90kcal、吃1.5个，服务端保存135kcal。名称、份数、每份kcal及P／C／F是常驻输入框，单击即可填写，输入与餐次备注持续显示柔和暖色边框。手机将单位／份数单独一行，营养两列。食材库点击或拖入，本餐合计常驻。

新每份输入用nutritionBasis=per_portion、perPortionNutrition和正数quantity；不能同时提交nutrition。旧接口的nutrition始终是本次摄入总量，旧餐不因份数再次乘。编辑旧自由项明确标注原口径，只有主动点“改为每份营养”才切换；转换先保留现有总量。旧misc／whole继续兼容，AI的whole仍须为整餐唯一项。

自由项详情是小框，只选择“标签／成分表”或“直接预估”，不另填重复补充说明；餐次备注保留。原详细依据继续留存，不补造推理。单位只出现一次，不再同时显示“填g”和“g”。新餐按设备时间建议餐次，用户可改，旧餐不覆盖。

## 食材与油酱

食材库直接列有效食材，名称、简短规格和实际基准数量常驻；蛋白质、碳水、脂肪、热量按列对齐，表头单位同行。营养值按该食材真实基准展示，不能把每包营养伪装成每 100g。依据、备注、来源和照片从最右侧“详情”打开只读抽屉；网页确认删除直接移除正式条目，不展示回收站；审计和既有软删除条目保持。

食材以 category:meal（整餐）／ingredient（食材）分类，库列表和录入选择器均可筛选；新增／编辑可指定，旧行默认 ingredient。基础预设及采用流程已移除，已入库条目保留。名称只保留去皮去骨、生重／熟重等核心规格。

同单位按基准换算；有可靠包装规格时，servingQuantity表示一包装对应的基准数量，servingUnit表示“包”等计数单位。默认1包、半包0.5，服务端换算；旧g记录与历史规格不改。没有可靠信息不猜一包多重。热量独立保存，未知为 null，历史营养和计量快照不随食材更新改变。手动自由项依据只有“标签／成分表”（reference）和“直接预估”（estimated）；AI 的 label／composition_table 仍须转录或来源链接，unknown 与旧来源不自动改写。描述只保留客观名称、每份分量与单位、成分和热量；估算食材保留成分分量、来源与计算、汇总结果，不写录入背景或凭空添加排除项。

纯食材、实际吃下的烹饪油、蘸酱分别记录。先核对做法与用量，再接受明确估算或未知；锅中投入的油不等于全部吃下，成品或整餐已经含油酱时不叠加。`amountDecision` 区分 provided、estimate_accepted、unknown_accepted；明确未知食量保留关联和 null 营养，不默认一份。

## 图片上传与恢复

每餐／食材最多 8 张、单张 20 MiB，支持原始 JPEG／PNG／WebP，不自动压缩。所有原图保存在 Private Blob，通过账号鉴权回看，不进入 public、Git 或营养 JSON 请求体。

MCP `import_meal_images` 和 HTTP `POST /api/v1/meal-images` 接受 ChatGPT files 引用，立即下载临时地址后私有保存，返回稳定 ID。最多两个下载并发，临时网络／5xx 最多重试一次，批次有截止时间；返回 complete／partial／failed、images、expectedImageCount 以及逐图 failures（index、code、stage、retryable、requestId）。部分成功保留已保存附件，只重试失败项。成功附件仍须加入对应餐次预览；已有餐次查询 id/version 后保留原内容更新。预览包含原图时应说明等待网页确认，确认后查询最新审核／餐次再报告关联状态，不把确认前文案当成实时状态。临时地址过期明确返回 image_url_expired，不能反复重用失效地址；服务端只下载允许的 ChatGPT HTTPS 文件域名，不接收任意外部／内网地址。除 oaiusercontent.com、chatgptusercontent.com、openai.com 的文件域名外，兼容 ChatGPT 的 oaisdmntpr 地区存储账号，例如 oaisdmntprnznorth.blob.core.windows.net 和 oaisdmntprwestus.blob.core.windows.net；Azure 账号名限 24 位小写字母／数字，限定完整前缀及 blob.core.windows.net 后缀。重定向每一跳重复校验，拒绝其他命名族、额外子域和伪装后缀。

网页使用 prepare → 短期 OIDC 预签名 → 浏览器直传私有 Blob → complete 登记。大图不经过 Vercel Function 请求体；凭据限定账号、随机路径、SHA-256、真实类型、大小和 10 分钟有效期，完成后核对实际字节，重复原图复用 ID。SDK 预签名流程不依赖 webhook。旧 multipart 客户端只兼容 4 MiB，需刷新使用新版直传。

网页显示进度、缩略图、失败原因及重试入口。照片未齐只提示，可以直接保存文字并之后补传，不需要额外勾选；expectedImageCount与缺图事实进入操作和审计。私有文件归属、实际字节和来源安全检查保留。未完成上传时仍保护草稿，不宣称原图已保存。

内容摘要、user_id、组合外键和 feature 校验保护重复及归属。编辑、软删除恢复、食材快照与审计保留原图；移除附件不销毁审计引用。

## AI 录入与审核

流程：上传原图 → 识别 → 查已有食材 → 集中核对必要信息 → 带图预览 → 网页确认。缺日期、餐次、身份或实际食用量先问，明确的信息不重复问。包装／一盘须确认实际吃下多少；标签核对品牌、每 100g／每份／整包、kJ／kcal，并保留转录及换算依据。用户明确接受的生重、油酱估算写入依据，不继续伪装成未解决问题。

普通AI记餐只生成餐次，明确要求入库才另生成食材库项目。确认页先日期、餐次、本餐kcal及P／C／F合计、食物，再显示修改与取消。只需底部一次“确认保存”，不要求“标记已核对”或五项照片勾选。photoReview仅保留兼容格式，不再作为保存条件；只对真实缺失信息、明确重复餐或未确定的运动包含关系提出对应问题。估算和未知保留，不强迫补精确值。

修改餐次时列清移除、增加、更改及修改后合计，原记录和完整内容按需展开；不能清空整餐。AI禁止整条删除／恢复及批量删除，网页手工操作保留；取消待保存项不删除已有事实。照片默认折叠并延后请求。

审核常驻日期、餐次、记录项数、食材库／自由填写数量、每项数量和四项营养。名称、份量和热量优先展示，估算份量使用“约”，不重复显示来源标签。每行最右侧“详情”区分引用已有食材、确认后新增入库及直接记录，避免把预览解析出的临时 ID 当成已有食材；展开后查看食物识别、份量、油酱与营养分别来自用户、标签、食材库、成分表、估算或未知，附可核实说明、来源与不确定性；旧记录只展示已有依据，不补造详细推理。

保存后审核显示“已保存”和结果，移除待确认与确认按钮。客户端按操作 ID、revision 和终态更新，旧 pending 响应不能覆盖完成状态；可加载最新审核状态，页面刷新仍从数据库读取。待确认入口只列实际未过期的 pending 操作，独立未处理提交不会因为另一条已保存而消失。15 分钟预览、凭据撤销、归属、版本、快照和幂等保护保持。

## 代码与维护

网页、HTTP、MCP 复用同一 feature。`model.ts` 管 schema 与换算，`records.ts` 管事务／预览／确认，`images.ts` 管下载与私有存储，`image-upload.ts` 管直传凭据和登记，`photos.tsx` 管上传／回看，`review-details.tsx` 管营养明细与依据，`records/record-review.tsx` 管统一审核状态，`meals-view.tsx` 管最近有效日／分页历史，`meal-editor.tsx` 管两种录入与单位联动，`nutrition-fields.tsx` 管营养及手动依据，`nutrition-chart.tsx` 管固定宽度图表与读数，`presets.tsx` 管食材表格／详情。

饮食和身体 Inspector 共用遮罩手势判断，拖选内容到外部不关闭。仪表盘根滚动容器预留 scrollbar-gutter；共用弹窗锁定 html／body，仅补偿实际释放的滚动条宽度，切页和弹窗不改变内容横向位置。食材表格和餐项按容器宽度转成紧凑行，数字与单位保持同行；历史抽屉直接展开食物，餐名旁显示热量、不重复四格汇总，备注和来源按需查看，不撑宽页面。

数据库通过 `0017_dry_pandemic.sql` 增加 foods.category 默认 ingredient 及枚举约束，保留所有旧字段和值。`0015_meal_review_images.sql` 保存 nullable review_explanation 和 20 MiB 原图约束；`0016_silly_adam_warlock.sql` 仅扩展 foods_source_valid 接受 reference，旧来源与所有既有值保持。共享 migration 不修改，旧记录不补造依据或原图预期。备份、发布与验收见 [部署说明](deployment.md)，当前状态见 [交接](../handoff.md)。

已授权的说明修正使用 `scripts/correct-meal-text.mts` 和 feature 内的 `text-maintenance.ts`，不开放公开维护 API。私有请求指定账号、食材／餐项 ID、版本及前后文字，先预览后绑定摘要写入；只改文字与版本，旧餐项软删除留存，原始请求、旧审计、营养、份量和照片保持。事务保存 AI 代执行者与前后快照，重复执行幂等，版本／原文／身份冲突或审计失败整批回滚。脚本用法见 [维护脚本](../scripts/README.md)。


`scripts/maintain-foods.mts` 和 `food-maintenance.ts` 用于已授权的指定食材分类／名称／说明与当前基准修正。预览绑定账号、ID、版本、关联餐次快照和摘要，事务写入并审计；原餐项软删除留存，原始请求与旧审计不改。当前 ON 标签基准为每 1 勺（约 30.4g），历史餐项的克数、单位、基准、营养和快照版本保持；仅与旧版本说明完全匹配的当前快照同步精简文字。Pasta Express 保留实际组成、各组食材的估计克数及整体热量范围和采用基准。不得按关键词批量重写历史。


食材详情以“估算分析”或“数据来源”为主体，不重复列表已有的四项营养表。估算依据保留组成与分量（含范围）、参考来源与可核实计算、整份结果；有标签／成分表时写来源标识和采用条目。未保存的分项克数／热量不补造，不用笼统一句估算取代已有分析，不写用户日期、上传或纠错经过，也不附泛化的生熟使用提醒。

`food-description.ts` 集中当前说明规则及明确污染文案的检查。新食材／foodDraft 含个人餐次背景或“不可直接套用／必须调整”等泛化提醒时，在建立预览前返回 `food_description`，可修正后沿用原 operationId 重试；个人备注仍可留在餐次，既有食材引用和历史快照不因该检查被改写。MCP search_foods 与 HTTP GET /foods 共用 queryFoods，每次实时返回 foodLibraryRules，避免只依赖客户端缓存的工具描述。自定义 MCP 元数据更新后应刷新连接并开新对话；刷新不会修改已保存文字。


## 最近删除与历史编辑

网页手工确认永久删除正式餐次或食材，原有回收数据不批量清理。删除食材断开全部版本餐项的food_id，保留营养、数量、原单位、包装快照和原图，不递增餐次版本、不作废当天已记完；缺少可靠快照则拒绝。旧餐编辑使用originalItemId解析服务端快照，不能从客户端伪造快照。删除餐次物理移除餐项及当前图片关联，并在同一事务作废当日确认。原始导入、审计、原图及备份保持；AI不获得永久删除权限。账号、版本、幂等和回滚保护继续适用。

## 手机每日记录与确认

每日记录包含最近10个日历日，空日直接补录，有餐次仍可添加一餐，并可选其他日期。编辑器与保存按钮标明目标日期；跨零点只更新今天，不改变草稿。空行不是已保存餐次，不向数据库补0。

AI确认按单餐展示日期、中文餐次、服务端kcal与P／C／F合计，再显示食物及次级操作。部分标已知部分，未知与0分开；修改逐餐列明增减和修改后总量，原内容按需展开，多餐不合成跨日总数。底部一次确认统一事务保存。照片和依据折叠，缺图、冲突和失败保留。手机确认页无四栏导航，首屏优先日期、总量、前两项与保存。

## 当天是否记完

饮食每天独立保存“已记完／未记全”；没有确认时显示“待确认是否记完”。在每日记录和日期详情中操作，不用逐餐重复确认。它与单项营养未知、AI条目已核对、某餐已经保存是不同状态。

总览由服务端统一判断：当天已记完，且摄入与最终消耗均有数值时才计算差值。营养字段部分未知或来源为估算继续沿用已知读数；P／C／F未知不额外阻断。未记全／未确认日仍保留摄入柱、读数和摄入线，以轻量斜纹／空心点提示，但盈余读数与线间填色留空。未知不是0，明确0正常参与。

新增、修改、改日、删除或恢复餐次，在同一事务让受影响日期重新等待确认；改日同时处理原日和目标日。确认绑定当前餐次版本，失败保留原状态，重复请求不覆盖后来的确认或新增。食材库规格修改不改写旧餐营养。

按用户确认，0023仅新增状态结构；一次性维护只为指定授权账号截至2026-10-23已有有效餐次的历史日期初始化“已记完”，空日不建、不补0、不改原餐次。初始化记录来源和审计，不成为未来默认；之后补录到旧日期也需要确认。新的确认入口仅限本人网页登录，AI保存餐次不自动确认全天。

实现：day-status.ts读取／更新与事务失效，meal-day-control.tsx呈现入口，model.ts组织每日汇总；meal_days与meal_day_events保存状态、当前餐次摘要、版本和可恢复审计。
